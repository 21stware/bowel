# Platform parity

What the desktop app does on each system, taking macOS as the baseline: every behaviour a `_darwin.go` file gives has a row. A row says either how the other systems do the same thing, why they have no need of it, or that it is left for later and why.

How far each implementation has been tried is its own column, because "it compiles" and "it has run" are different claims:

- **macOS**: developed and run on.
- **Linux**: the package tests run on Ubuntu 24.04 (arm64, kernel 6.8), unprivileged and with no desktop session. Anything that needs a desktop (polkit's dialog, GNOME's or KDE's settings, the tray, a screenshot tool) or root on a real network (the TUN device itself, forwarding) has **not** been run on hardware. Gateway mode is the exception: `scripts/gateway-e2e.sh` runs it as root in containers, with a real TUN device, real forwarding and a device behind it (see [gateway.md](gateway.md)).
- **Windows**: cross-compiled and vetted, with the logic that needs no Windows API tested on other systems. **Nothing has run on Windows on our side**; what is known from a real machine comes from users' reports, noted where it applies.

## By application: rules, and Android's exclusion list

Two things go by this name, and only the first is in the table above.

| | macOS | Linux | Windows | Android 10 and later | Android 8 and 9 | iOS |
| --- | --- | --- | --- | --- | --- | --- |
| A rule that sends an app to a route group (`routes.KindApp`) | yes | yes | yes in code, not run by us | yes: the VPN service asks the system which app owns a connection, for the core | no: the system gives no way to ask; a rule brought over from a desktop is kept, shown, and can be deleted | not released |
| A list of apps that stay outside bowel | none | none | none | yes | yes | not released |

The list on Android (Settings, "Apps that skip bowel", 不走 bowel 的 App) only excludes: `BowelVpnService` calls `addDisallowedApplication` for each package when the VPN starts, so a change applies at the next connection, and an excluded app connects directly where no rule sees it. There is no mode that proxies only chosen apps (`addAllowedApplication` is not used). The app refuses a rule for a package on the saved list, and marks a rule whose app was put on the list afterwards; both read the saved list, not what the running VPN started with, which is why their words say "after a reconnect".

## Not needed, and why

- **Which app owns a connection** (`internal/procinfo`). mihomo names the process behind a connection itself, on every system. `procinfo` exists because macOS 27 shows the kernel's socket list only to a process signed under an identifier with a dot whose parent is not an app, which the core was not; bowel, opened like any app, read the list for it. The core is now started detached and its file named so that a release build signs it as `dev.moho.app.core` (`docs/architecture.md`, Monitoring), and it reads the list itself; `procinfo` still names the connections the core does not look up, and those of a core signed otherwise, such as one signed by an Apple Development identity, as `mygo dev` signed it until MyGo 0.9.1, which no combination tried on 27.2 let see the list (#131). Linux (`sock_diag` and `/proc`) and Windows (`GetExtendedTcpTable`) put no such limit on the core, so the monitor's fallback is never asked.
- **Dock icon** (`syncDock`), **flag drawing** (`flagdraw_darwin.go`), **quit pump** (`quit_pump_darwin.go`). The first is the Dock's, which the other systems do not have. The second works around how macOS's text system colours emoji flags; elsewhere the plain drawing is right. The third keeps AppKit's run loop turning during a quit.
- **Screen Recording permission**. Only macOS keeps the screen behind a permission of its own. Elsewhere a capture that fails says so.

## Left for later, and why

- **Gateway mode on Windows.** Three things are missing, and each needs trying on Windows before it is written. Windows forwards per adapter: both the LAN's and TUN's must be switched, and TUN's is made anew each time. Nothing like a sudoers rule lets a user's process do that unelevated, so it would take a second task or a service. And the firewall drops what arrives to be forwarded, and the resolver's port 53, until rules are added. The interface does not offer the gateway on Windows.
- **The system's DNS servers under TUN, on Windows and on Linux without systemd-resolved.** The condition macOS had (issue 117) is the same wherever the system's resolver is an address of the LAN: developer networks keep the private ranges out of TUN (`route-exclude-address`), so a query to the router never reaches `dns-hijack`, the system gets real addresses in place of fake ones, and no rule that names a domain matches. On Linux without systemd-resolved the file to change is `/etc/resolv.conf`, which is root's and often another program's (NetworkManager, `dhcpcd`, `resolvconf`); bowel only reads it and tells the user. On Windows the core sets the TUN adapter's DNS, and whether the system then still asks the LAN adapter's server has not been tried on a real machine, so nothing is set or said there.
- **Developer tools on Windows.** The model is another one: terminals are PowerShell and cmd, whose environment is the user's registry (`HKCU\Environment`) and a profile script; OpenSSH for Windows has no `nc` to call. Nothing is read or written there, and the section is not shown. Download sources work.
- **The system's Docker daemon on Linux.** Its proxy is `/etc/docker/daemon.json` or a systemd drop-in, both root's, and takes a restart of the daemon. Colima's, which bowel does connect, is a file of the user's.
- **Camera on Linux and Windows.** Video4Linux and Media Foundation are each a capture pipeline of their own; the screen and picture files cover the same use meanwhile.
- **System proxy on other Linux desktops** (sway, Hyprland, Xfce with no GSettings schema). There is no setting to write; programs there follow environment variables, which the terminal's connection under Developer tools sets.
- **A polkit action of bowel's own.** `pkexec` shows its generic text ("run /bin/sh as the super user") since bowel installs no policy file. Packaging one in the `.deb` and `.rpm` would let the dialog say what it is for.

## Privileged paths

The rules are the same on every system: the authorisation is asked once (on Windows, for TUN, at every start of its core: see below), it grants the narrowest thing that works, and what bowel changed is put back, also after a crash.

| | What root (or elevation) does, once | What it leaves | Undo |
| --- | --- | --- | --- |
| macOS TUN | `chown root:admin`, `chmod 4755`, `mv` | setuid core in the data directory | delete the file |
| Linux TUN | `chown root:root`, `chmod 0755`, `setcap`, `mv`; with systemd-resolved, `install` of the rule | core with three network capabilities, running as the user; `/etc/polkit-1/rules.d/49-bowel-tun-<uid>.rules` | delete the two files and `bin/tun-dns-rule` beside the copy; removing the package (`.deb`, `.rpm`, AUR) deletes every user's rule |
| Windows TUN | at every start: the launcher; and first, when the copy is missing, another build's or not closed to the user, `mkdir`, `icacls` (owner and rights of the copy's folder and of the two above it), `schtasks /End` and `/Delete` of the tasks earlier versions registered, `copy`, ending a core still running from the copy | protected copy and `bowel-tun.exe` beside it | delete the directory |
| macOS, Linux gateway | `install`, `visudo -c`, `mv` | `/etc/sudoers.d/bowel-gateway-<uid>`: two `sysctl` commands | delete the file |

On Windows TUN is the exception to "asked once". Versions up to 0.4.9 asked once and registered two scheduled tasks that ran the copy at the highest run level whenever bowel started them. On a stock Windows 11 Pro (26300, Defender with cloud protection, behaviour monitoring and tamper protection on) the first `bowel tun on` of 0.4.8 got `bowel.exe` quarantined as `Behavior:Win32/Persistence.A!ml`, which also took its shortcuts, its Run key and its Uninstall entry. A probe doing the same under other names was flagged 5 to 15 seconds after it registered a task (with bowel's two tasks, with a separate launcher, and with a single S4U task running the core alone), and not flagged when it only copied itself into `%ProgramData%` and ran once elevated with no task. Defender's log shows behaviour reports sent at the task's registration, then a cloud query on the hash of the unsigned program that registered it, then the block. So nothing is registered any more: each start of TUN's core is elevated through a UAC prompt of its own, and starts with TUN on, after TUN was turned on while the bundled core ran, after a crash and after an update each show one. Turning TUN off and on while the elevated core runs is a reload, with no prompt. Tasks can come back once the Windows builds are signed.

What the prompt elevates is never a file the user could have changed. The launcher is elevated directly only when the copy is current: the mark written by the command that made it (`installed`, which also says that the old tasks were deleted), the core and the launcher the same bytes as the bundled core and the running `bowel.exe`, no core still running from the copy, and nothing the user's own programs could use to change it. That last is asked of Windows, not read off the ACL: the unelevated bowel tries to open the two files, their folder and the two folders above it with each right that would let it replace them or what is in them, and any right granted, or any answer other than a refusal, sends the start through `cmd.exe`, which takes the folders back for the administrators and makes the copy again. The launcher starts no core but the one beside it. It ends the core with bowel because the handle an unelevated process gets on an elevated one may lack the right to end it: bowel passes its process id, its creation time and the value of an unnamed event handle; the launcher opens bowel's process, copies the event out of it, and waits for the event, bowel's end or the core's. Only a program that could open bowel's process to copy its handles can set the event, and setting it only ends the core.

Uninstalling has nothing to remove but the folder; it also deletes the tasks of an earlier version, which the first start of this one has deleted already.

The polkit rule on Linux exists because the core, with `auto-route`, points systemd-resolved at its resolver for the TUN device each time the device comes up (`resolvectl domain`, `default-route`, `dns`) and takes that back when it goes (`revert`). Those are polkit actions that ask for an administrator, and file capabilities mean nothing to polkit, so a core running as the user brought three password dialogs at every start (issue 71). Skipping the calls (`dns-mode: disabled`) is not the way out: resolved would go on asking the network's own servers over sockets bound to the physical link, past TUN. The rule names the user and, where polkit is told the link (systemd 256 and later), the TUN device; with an older systemd it allows that user the four actions on any link. That adds little to what the copy already gives, since whoever may run it can route every packet of the machine. Its text is kept beside the copy (`bin/tun-dns-rule`), the mark that the rule was written; where polkit's directory refused the rule, the mark ends in a line saying so, and that machine is not asked again. Before TUN starts bowel also reads the rule itself and compares it with what it would write, so a rule deleted or edited by hand is written again under one authorization. That works only where the user may read `/etc/polkit-1/rules.d`: where the directory is closed to users (the report on issue 71 needed `sudo` to list Fedora 45's, which suggests it is; not confirmed), the mark is taken at its word, and a rule deleted there goes unnoticed until the mark is deleted too. Removing the package deletes the rules of every user (`scripts/linux-postrm.sh`), and leaves the copy and the mark in each home, as it leaves the settings. What a missing rule costs is not only the dialogs. Without it, and with the dialogs dismissed or with no polkit agent to show them, the core's three `resolvectl` calls fail, and the core does not look at their result: the device is up, the routes are there, and systemd-resolved still asks the network's own servers. Lookups then do not reach the core, so nothing gets a fake IP, and traffic that does not use the proxy port is routed by address alone: rules by domain silently do not apply to it, while what uses the port works, which makes it look like a routing fault (issue 117, an upgrade from 0.3.0 with TUN on). bowel tells of it in two ways while TUN is on. An installation that lacks the rule is said to lack it, with the authorization offered, as a stale core is. And every 10 seconds, from 15 seconds after the core started, bowel reads `resolvectl dns <device>`: two looks in a row that find the link without servers put "System DNS isn't pointed at TUN" in the TUN entry's detail (`takeover.tun.detail` in `bowel status --json`) and in the notice, whatever the cause, including a rule that is there and that polkit does not honour. A link seen with servers ends the notice even without the rule (the user answered the system's dialogs); no answer from `resolvectl`, no such device, or output in another form is taken as not known, and says nothing. The entry's status stays `on`: TUN is on. Nothing is written where the core runs as root, where `resolvectl` is missing, or where polkit reads no `rules.d` (0.105 and its `.pkla` files): there the dialogs stay.

With the tasks went what they needed: the second task, for a domain account whose S4U logon fails away from its controller (issue 66), since a UAC elevation asks no controller; the `tun-task` file that remembered which task worked; the `no-fallback` file and the hint for a registration that security software refused (issue 117, 360 Total Security). What this costs: a prompt at every start, which a session with nobody at the desktop cannot answer (`bowel daemon` over SSH has no TUN on Windows now), and while it is up the core is not running, so the network through bowel waits for the answer. Windows cancels a prompt nobody answers after about two minutes, which reads as a refusal: the bundled core then runs, and the TUN entry says so. A prompt asked for with no window of bowel's in front goes to the taskbar, where at a start with the window hidden (at login) nobody saw it, so before asking bowel brings its window forward, gives it as the prompt's owner (`SHELLEXECUTEINFO.hwnd`), flashes it in the taskbar, and says on the TUN entry (`takeover.tun.asking`) what it waits for and that Windows cancels it.

An earlier version's task may still run its core when this version starts (that version crashed or was ended), holding the ports and the adapter, and the elevated command that would end it only runs once a prompt is answered. So before any core starts, while the copy's mark is still an earlier version's, bowel ends both tasks unelevated (`schtasks /End`, which the user may do with their own tasks, as those versions did at every start) and waits a moment for the core to go; deleting the tasks is left to the elevated command. That command moves the copies it replaces aside (`mihomo.exe.old`, `bowel-tun.exe.old`), since a running program's file can be renamed but not written, and the launcher deletes them at its next start, elevated, which the user could not.

At run time: forwarding as it was is kept in `gateway-before.json` and put back when the gateway goes off or on the next start; the system proxy as it was is kept in `sysproxy-before.json` and restored on quit; on macOS every network service's DNS servers as they were are kept in `dns-before.json` and put back when TUN goes off, on quit, or on the next start; TUN's routes go with the core's process. On Windows the launcher ends TUN's core when bowel's process ends, crash or not, so none is left running.

### macOS: the system's DNS servers under TUN

A network usually hands out its router as the resolver. That address is on the LAN, which TUN leaves out, so with nothing done the system's queries go past `dns-hijack` (issue 117). While TUN is on with something to hijack, bowel therefore sets the DNS servers of every enabled network service to `223.5.5.5` and `119.29.29.29`. Which addresses they are matters little: any address that routes into TUN is answered by the core in its place. Public resolvers were chosen so that names still resolve should they ever be left behind.

- It needs no authorisation: `networksetup` sets them as the user, as it does the system proxy. This is a setting of the system that persists, which is why it is undone with care.
- Except on a Mac with "Require an administrator password to access system-wide settings" turned on (System Settings › Privacy & Security › Advanced…, off by default). There `networksetup` changes network settings only as root, and says `Command requires admin privileges.` to the user (issue 189). Both the system proxy's entry and the DNS notice then say that this option is the cause and where to turn it off, in place of `networksetup`'s words. Nothing is elevated yet: a rule that lets bowel make these changes on such a Mac is still to be decided.
- What each service had (its own servers, or none, which means what the network hands out) is written to `dns-before.json` in the data folder before anything is set. A service that already has the placeholder keeps the first copy.
- It is put back when TUN goes off, takeover is paused, the TUN core does not start, the setting is turned off, or bowel quits. After a crash the next start does it, or, if TUN is to be on again, carries on from the first copy. Only a service that still has the placeholder is written: one the user or another program has changed since is theirs.
- Every 20 seconds, with the networks, bowel looks again: a service that appeared since gets the placeholder, and a restore that did not finish is tried again.
- The names that are the system's to resolve (`*.lan` and the like, under Developer networks) are asked of the network's own servers, which bowel kept, since the core's `system` would now be the placeholder. Domains the system splits off to servers of their own (Tailscale, a company VPN, `scutil --dns`) are not network services' settings and stay as they are.
- "Take over system DNS" under Settings, TUN (`tunKeepSystemDns` in `bowel settings`) turns it off. Then, and when the system refuses the change, the status says that the system's DNS goes around TUN whenever its first server is an address TUN leaves out.
- To undo it by hand: `networksetup -setdnsservers Wi-Fi Empty` for each service, and delete `dns-before.json`.

Not tried: an account that is not an administrator (macOS may refuse `networksetup` there; the status would say so), a network behind a captive portal (as with TUN in general, its sign-in page may not open until TUN is off), a network whose only resolvers are IPv6 addresses from router advertisements (they are not in the lease bowel reads for the network's own names), and a VPN whose resolver is the system's default (it is no network service's setting, so the status would only tell).

## Not yet run on a real machine

Linux:

1. The polkit dialog and the whole `pkexec` installation, on a desktop session. (The commands' quoting ran in `sh`, and reading capabilities was checked against a file `setcap` really marked.)
2. The core opening a TUN device with file capabilities alone, with `auto-route`, on a real network; and the same on a home directory mounted `nosuid`, which should be refused. A user's report on Fedora 45 with KDE (issue 71, bowel 0.3.0) covers the first half: the `pkexec` installation ran as written and the device came up, with three polkit dialogs from the core's `resolvectl` calls. The rule written since has **not** been read by a real polkit: its text was only run in another JavaScript engine against a stand-in for polkit's objects. Open: that polkitd accepts it, that systemd 256 and later pass the link as `interface`, that `revert` at TUN off is covered, and what re-created the device in that report after a dismissed dialog (the core ignores `resolvectl`'s result, so it was not a retry of it). Nor has the look at `resolvectl dns <device>` met a real systemd-resolved: its parsing ran on sample output in the form the split-DNS detection already reads, and the notice for an upgraded installation without the rule (issue 117) ran only in unit tests, as did the wording for `pkexec` with no agent (its two messages are taken from polkit's source, not from a run). Also not run on a desktop: `Uninstall` removing the rule through `pkexec`, the second authorization after a rule deleted by hand, and the removal script in a real `.rpm` or the AUR package (the `.deb`'s ran in the VM, in a stand-in package: rules kept on upgrade, deleted on removal).
3. System proxy on real GNOME and KDE sessions (tested against stand-ins for `gsettings` and `kwriteconfig6`), including whether running programs pick the change up.
4. Gateway mode end to end: the sudoers rule through real `sudo` (the rule passes real `visudo`), forwarding with TUN's rules in place, and the resolver on `0.0.0.0:53` beside systemd-resolved's stub on `127.0.0.53`.
5. Split DNS from `resolvectl` on a machine that runs systemd-resolved, and Tailscale's routes in table 52 (parsed from samples).
6. Screen scanning with each screenshot tool, on Wayland and X11; the tray.
7. `ping` (the test machine has none installed).
8. The notice that the system's DNS goes around TUN, on a machine without systemd-resolved whose `/etc/resolv.conf` names the router (the parsing is tested; the test machine has no such file).

Windows, all of it on our side. TUN's start through a UAC prompt at each start is new, and has **not** been run elevated: the tests ran it as the user, with the prompt replaced by a plain start. They ran a real launcher (the test binary) that started a stand-in core in its job, ended it when the event was set and when its app was killed; `Spawn` finding the core under the launcher, `Stop` and `Wait`; `cmd.exe` running the command that makes the copy, stopped by the first owner change as the user is, with that step and Windows' words read back from the log; and the rights check, which finds a copy in the user's own folder open and `System32` closed. In the order they would fail:

1. The prompt for `bowel-tun.exe` and for `cmd.exe`, `icacls` taking the folders above the copy back for the administrators, `start "" /wait` returning the launcher's exit code, and `2>>` keeping what `start` says of a launcher it cannot run.
2. The launcher, elevated, opening bowel's process (`PROCESS_DUP_HANDLE`) and copying its event; then the core ending when TUN's core is stopped, when bowel quits and when bowel is ended from Task Manager.
3. An unelevated bowel finding the copy closed (the rights check), so that the second start's prompt names `bowel-tun.exe`, not `cmd.exe`; and the first start after an update from a version with tasks deleting both.
4. The core finding Wintun from an elevated, hidden process in the user's session, and Defender's verdict on all of it: the probe that copied itself and ran once elevated was not flagged, bowel itself has not been watched doing it.
5. The log through the controller, as before.
