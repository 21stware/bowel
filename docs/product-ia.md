# Moho 产品信息架构（v1.6）

> 这份文档只讲产品逻辑：用户要做什么、产品里有哪些对象、信息分几层露出。
> §6 的决策已确认（2026-11-07），按推荐方案执行。
> §9 写于 2026-11-22：范围、应用代理、专用浏览器窗口、服务包、`bowel://` 链接和隔离还缺的几处已商定；维度放在哪、排序、虚拟全局和预置服务的名单仍是提案。确认后 9.15 的 D7–D10 并入 §6。

## 0. 一句话定位

**让该走代理的流量走最好的出口、其余直连；同时让用户随时知道现在是什么状态，出了问题能自己定位。**

由此得出三条设计原则，后面每个决定都要对得上：

1. **状态先于控制**：先告诉用户"现在是什么情况"，控制只出现在对应的状态旁边。
2. **正常时安静，异常时显眼**：一切正常时界面应该很平静；只有出问题时才弹出提示。不常驻告警卡片。
3. **每条信息只有一个家**：同一个信息只在一个地方完整展示，其他地方只放摘要并链接过去。

## 1. 核心对象模型

所有界面都是在看同一条链路：

```
应用 ──► 入口 ──► 规则 ──► 路由 ──► 节点 ──► 互联网
(谁)    (怎么进来) (怎么判断) (该去哪类出口) (具体走哪台机器)
                                      ▲
                                  Provider（节点从哪来）
```

| 对象 | 是什么 | 用户关心的属性 | 用户能做的操作 |
|---|---|---|---|
| **入口** Entry | 流量怎么进入 Moho：系统代理、TUN、本地端口 | **是否真的生效**（不是"开关开了没"） | 选择接管方式；修复异常 |
| **规则** Rule | 判断一条请求属于哪条路由：域名 / GeoSite / IP / 进程 | 命中了哪条 | 查看；少数情况下新增或修改 |
| **服务** Service | 一个网站或产品需要的一组规则，例如 Claude、Netflix。一条规则只属于一个服务，一个服务只属于一个路由组 | 属于哪个路由组 | 移动、停用、新建 |
| **路由** Route | 一类流量的去处，例如「AI 服务」「流媒体」「默认」「直连」 | **当前出口节点、健不健康** | 换节点、换选择策略 |
| **节点** Node | 一台具体的出口服务器 | 地区、延迟、稳定性 | 选中、测速 |
| **Provider** | 节点的来源：订阅链接、单节点链接、本地文件 | 能不能用、还剩多少流量、什么时候到期 | 添加、更新、停用、删除 |
| **模式** Mode | 对「规则」这一步的全局覆盖：规则 / 全局 / 直连 | 现在是不是特殊模式 | 临时切换 |
| **内核** Core | mihomo 进程 | 只关心"是否正常" | 重启、更新（极少） |

**命名统一**：界面上只用「接管、入口、路由组、服务、节点、Provider、规则、模式」这几个词（「路由组」就是这里说的路由）。不出现「代理组」「策略组」「Selector」这类 Clash 术语，它们只出现在高级视图里。

### 1.1 关于「路由」

Clash 的「代理组」是实现层面的概念：组可以嵌套、类型一大堆。用户脑子里的模型其实是：

> **「这类流量」→「走这个出口」**

所以路由的主表达就是一句话：**`AI 服务 → 🇺🇸 洛杉矶 VPS · 168 ms`**。
怎么挑节点（自动最快 / 顺序备用 / 固定节点）、候选节点有哪些、命中哪些规则，都属于第二层信息。

## 2. 状态模型（回应第 4 点）

你说得对：系统代理、TUN 不应该做成开关，它们应该是**状态**。

用户真正的操作只有一个：**接管 开 / 关**。用哪种方式接管（系统代理 / TUN / 两者都用）是偏好设置，很少改。界面要如实反映的是每个入口的**真实状态**，而不是用户点过什么：

| 入口 | 可能的状态 |
|---|---|
| 系统代理 | 未使用 · **生效中** · **被其他程序改掉了**（系统代理已不指向 Moho） |
| TUN | 未使用 · 需要安装服务 · **生效中** · 异常（服务掉了、权限丢了） |
| 本地端口 | 监听中 `127.0.0.1:7899` · 端口被占用 |

把这些合成一个**总状态**，全产品只有这一个灯：

| 总状态 | 条件 | 表现 |
|---|---|---|
| ⚪ 未接管 | 用户关了接管 | 灰色，提示"应用直接连接互联网，除非代理指向 Moho 的端口" |
| 🟢 正常 | 至少一个入口生效，内核正常，各路由当前节点都可用 | 安静，只显示出口和速度 |
| 🟡 降级 | 能用，但有问题：某路由的节点在超时、发生了故障转移、Provider 快到期 | 一句话说明问题 + 一个处理入口 |
| 🔴 异常 | 流量实际走不通：内核挂了、入口被改了、所有节点都不可用 | 显著提示 + 一键修复（例如"重新接管"） |

> **未接管不等于没有流量。** 接管关着时内核和本地端口照常工作，把代理手动指向本地端口的应用，流量仍然经过 Moho。所以"未接管"只描述入口，不描述流量：事件、流量图、连接数、菜单栏面板的网速都按**实际观察到的**连接和历史来显示，不看接管开关；只有什么都没观察到时才显示"没有流量"一类的空闲文案。任何时候都不能在列着连接或历史的地方写"流量不经过 Moho"。菜单栏面板（和 Linux 的托盘菜单）在未接管但观察到流量时也列出节点：这些流量从这里选的节点出去。
>
> 这里的"状态"需要客户端**主动检测**：比如定时检查系统代理是否还指向自己，因为其他 VPN 或代理软件经常会把它改掉。这是 Clash 系客户端普遍缺失、而用户很需要的能力。

## 3. 任务分析

按频率从高到低排，决定每个任务放在哪一层：

| # | 用户任务 | 频率 | 典型触发 | 放在哪层 |
|---|---|---|---|---|
| T1 | 确认现在正常、走的哪里 | 持续 / 每次看 | 下意识瞥一眼 | **L0 菜单栏** |
| T2 | 看当前速度 | 持续 | 下载东西时 | **L0 菜单栏** |
| T3 | 打开 / 关闭接管 | 每天 | 开会、用公司网络 | **L0 菜单** |
| T4 | 给某类流量换个节点 | 每周几次 | 节点慢了、想换地区 | **L0 菜单**（快捷）/ **L1** |
| T5 | 临时切全局或直连 | 偶尔 | 排查、临时需要 | L0 菜单 / L1 次要位置 |
| T6 | 处理异常（节点挂了、被改了、到期） | 偶尔但紧急 | 异常提醒 | 提醒在 **L0 / L1**，处理在 **L2** |
| T7 | 排查"某网站打不开 / 走错出口" | 偶尔但关键 | 网页打不开 | **L2 活动** |
| T8 | 测速、挑节点 | 偶尔 | 选节点前 | **L2 路由详情** |
| T9 | 添加或更新 Provider | 每月 | 买了新机场 | **L2 Provider** |
| T10 | 让某个域名走某条路由 | 少 | 排查之后 | **L2**（从活动里一键生成规则，规则落在该路由组的「我添加的」） |
| T11 | 新建或编辑路由组、服务、规则 | 很少 | 重度用户 | **L2 路由组 Tab** |
| T12 | 端口、TUN 服务、内核、开机启动 | 很少 | 首次设置 | **L3 设置** |

## 4. 渐进式披露

| 层 | 载体 | 回答的问题 | 内容 |
|---|---|---|---|
| **L0** 一瞥 | 菜单栏图标 + 下拉菜单 | "正常吗？" | 图标只分亮 / 暗（接管开 / 关），旁边默认不放网速（设置里可以打开，见下）；面板里一级就是换节点、接管开关、模式三件事（不放路由，路由在主窗口），没有动画；打开主窗口 |
| **L1** 一屏 | 主窗口首屏，不用滚动 | "现在什么情况？" | 总状态 + 出口；实时流量；路由一览（每条一行）；只在有问题时出现的异常条 |
| **L2** 详情 | 抽屉、详情页、Tab | "为什么？怎么改？" | 路由详情（候选节点、策略、命中规则）；路由组（服务、规则、节点策略）；活动（连接 / 日志）；Provider 详情；入口状态详情 |
| **L3** 高级 | 设置、高级编辑 | "我要定制" | 端口、TUN 服务、内核、原始配置 |

**L1 只有一屏**：如果首页需要滚动，说明 L1 放了 L2 的内容。

### 4.1 每一层的内容清单（L0 / L1 详细）

**L0 菜单栏**

```
[图标]                              ← 亮 = 已接管，暗 = 未接管；不带角标，默认不带网速
──────────────────────────
● 正常 · 全局模式             [■]    ← 总状态 + 唯一的开关；开关生效、内核启动期间状态字 shimmer
↓ 2.5 MB/s  ↑ 212 KB/s    今日 2.4 GB
──────────────────────────
节点                                  ← 「其他流量」出口的节点，就地列出，点一下就换
✓ 自动  最快 + 故障转移
  🇭🇰 香港 03 IPLC       当前  41ms
  🇭🇰 香港 02                  64ms
  …最快的 8 个
  全部节点…                    42 个
──────────────────────────
模式               规则 / 全局 / 直连
──────────────────────────
打开 Moho                      ⌘O
退出 Moho                      ⌘Q
```

图标旁默认什么都不放：看网速点开面板。想一直看着网速的人可以在「设置 › 通用」里打开「在菜单栏显示网速」，接管时（或者未接管但有连接经过本地端口时）图标旁多一段定宽的文字（`↓1.3M ↑ 60K`，没人看着时每 2 秒更新一次）；Windows 的托盘图标旁放不了文字，网速放在悬停提示里；Linux 上只有会显示 indicator 文字的面板才看得到。

面板不放路由：给某条路由换节点在主窗口（L1 / L2）。面板里没有动画，点开、切换、关闭都直接到位。

**L1 主窗口首屏**（v1.2 修订：按"杂志 + 可视化"组织，三层重要性从上到下）

| 层 | 内容 | 表现 |
|---|---|---|
| ① 标题级 | **当前出口节点**、**代理模式**、**接管方式** | 出口用大号衬线标题（"香港 03 IPLC"）+ 延迟和稳定性；右侧是一张出口地图，从"你"出发，每条路由一条弧线，粗细代表流量，光点代表正在传输的数据 |
| ② 就地切换 | 换节点 / 自动选最快；模式 规则·全局·直连；接管 系统代理·TUN；各分流路由的出口 | 不另开页面：点节点名弹出按延迟排序的列表；模式和接管方式是"可点的词"，选中的为实色并带下划线 |
| ③ 状态与监控 | 此刻速度（按路由着色的柱图）、谁在用、刚刚发生了什么（实时事件流） | 小字号、高密度；"全部活动 →" 进入活动页 |
| 快讯条 | 仅降级或异常时出现在标题栏下方 | "异常 · 系统代理被其他程序改掉了 [重新接管]" |

> 修订说明：v1.1 把"实时速度"放在最显眼的位置，但用户打开主窗口最想确认的是"走哪个出口、什么模式、怎么接管的"，速度属于第三层。

**L2 路由详情**（从 L1 点进来）

1. 头部：路由名 → 当前节点、健康度、选择策略
2. 候选节点：按地区分组，显示延迟和稳定性（最近 N 次测速）
3. 命中的规则：摘要，例如"openai.com、anthropic.com 等 12 条"，可以展开
4. 这条路由当前的连接：链接到活动页，并带上筛选条件

**L2 活动**：连接 / 日志 两个 Tab，共用筛选（应用、路由、失败）。
从一条连接可以一键"让这个域名走 XX 路由"，这一步会生成规则，放进该路由组的「我添加的」，在路由组 Tab 里管理。

**Provider：第三个 Tab**（v1.3：弹窗改为 Tab）。上方是添加栏（粘贴订阅链接或节点链接，自动识别；也可以选本地文件），下方是 Provider 列表：用量、到期、节点延迟分布、自动更新、更新 / 停用；点开一行显示它的全部节点、实测出口位置、被哪些路由使用。在任何页面按 ⌘V 粘贴链接会跳到这里并填好内容。

## 5. 导航结构

```
Moho
├── L0 菜单栏
└── 主窗口
    ├── 代理（L1）                 ← 默认页；每个区块都能原地展开（L2）
    │   ├── 出口 → 选择出口  ← 地区筛选、搜索、全部测速、自动 / 手动
    │   ├── 地图 → 各路由出口一览
    │   ├── 模式 → 模式与规则
    │   ├── 接管 → 系统代理 / TUN / 本地端口的详细状态和开关
    │   ├── 分流 → 路由一览 → 某条路由的选择出口
    │   └── 速度 / 谁在用 / 刚刚 → 各自的完整视图
    ├── 活动（L2）：连接 | 日志
    ├── Provider（L2）：添加 + 列表
    ├── 路由组（L2，⌘4）：路由组 → 服务 → 规则，节点策略，测试一个地址
    └── 设置（L3，⌘, 独立窗口）
        ├── 接管方式（系统代理 / TUN / 两者）、端口、局域网
        └── 通用：开机启动、外观、内核
```

**首次启动**：窗口打开时一个来源都没有，就不显示标签页，而是整窗的初始化页，分两步：添加节点（和 Provider 的添加栏收同样的内容）、选择接管方式。接管后或点跳过进入今日。只在窗口打开时判断一次，之后删光来源仍留在 Provider 页。

**对导航形式的影响**（回应第 3 点）：顶层只有 3–4 个目的地，而且 L1 就能完成大多数任务，所以**不需要常驻侧边栏**。标题栏里放一个分段控件，或者用工具栏图标就够了，主内容可以占满宽度。具体形式到界面阶段再定。

## 5.1 交互约定（v1.3）

- **区块原地展开（morph + 挤压）**（v1.4，取代 v1.3 的底部抽屉）：首页是一整张网格面板，被点的区块在面板里原地长大，同一行的区块被压窄，同一列的被压矮，其余的两个方向都被压缩；被挤压的区块换成"摘要"视图（标签 + 一个最重要的值），点它可以直接切过去。每个区块有三种视图：正常（固定尺寸，挤压时不重排、只淡出）、摘要、展开，三者交叉淡入淡出；展开内容第一次出现时逐行错开浮现。地图在形变过程中按实时尺寸重绘。Esc 或 × 收起。
- **未接管时收拢**：未接管时面板只剩标题区和地图：大字"未接管"、一句说明、两个接管方式（系统代理 / TUN）和"上次使用"。其余区块的行高收为 0；接管成功后整个面板展开回来。
- **被挤压的区块必须完整**（v1.6）：先算出每个区块形变结束时的尺寸，再按尺寸选版式，内容按版式设计成一定放得下，不靠截断：
  - 窄矮：标签 + 一个短值（如"实时"、"■■■ 3 条"）；
  - 宽矮：标签，下一行是值 + 一句说明；
  - 窄高：标签、值、说明、列表，允许换行；
  - 宽高：同窄高，值的字号更大。
  原型里逐一检查了 8 种展开状态下所有被挤压的区块，零溢出。
- **视图在最终尺寸下排版，像抽屉一样开合**（v1.6）：每个视图（正常 / 摘要 / 展开）都固定为它所在区块在最终状态下的尺寸，比如行一开始就是全宽，形变过程中不重排、文字不被挤压。新视图在预期位置由上而下逐行拉开；离开的视图按自己原来的尺寸向上收起，然后才清空。
- **顶栏**（v1.6）：标题栏和内容之间不画分隔线，二者是同一张纸；Tab 做成一个分段控件，当前项是墨色实底；右侧状态也是同形制的小药丸。
- **共享元素过渡：不交叉淡化，"实"的形变**（v1.5）：
  - 同一个东西在每个视图里有同一个身份（`data-m`），比如每个区块的标签、出口节点名、路由名、接管方式、模式下划线、应用名、速度。
  - 切换时先量出旧位置，再量出最终布局（网格动画的终点），然后用一份**真实文字**的克隆从旧位置飞到新位置，字号、颜色、字距逐帧插值。文字每帧重新排版，始终清晰；真实元素在落地前隐藏，所以任何时刻每样东西只出现一次。
  - 文字内容变了：原地的用遮罩滚动替换（旧的向上滑出，新的从下方滑入）；位置也变了的，旧文字在原处被擦除，新文字边飞边擦入。
  - 视图之间不做透明度渐变：旧视图立即隐藏，新视图随卡片长大被"露出"，非共享的行带短促的上浮错开进入。
  - 地图弧线、粗细、透明度缓动到新目标。
  - 不用 View Transitions：它是新旧两张位图的交叉淡化加缩放，会有重影，文字也会发糊。
- **加载态用流光（shimmer）**：所有需要时间生效的切换，在生效前把对应的文字做成流光，不用转圈。包括：系统代理 / TUN 开关（TUN 首次还要安装提权服务，文案提示"请在系统弹窗中确认"）、换节点（标题和延迟同时流光）、切模式、测速（延迟数字变成骨架条）、更新 Provider、重新接管。
- **活动页的查询能力**：搜索支持 `app:` `route:` `node:` `host:` 语法，其余词匹配任意字段；按状态（活跃 / 已关闭 / 失败）、路由、应用、TCP/UDP 筛选；速率、下载、上传、时长可排序（大的在前），应用、目标、命中规则、路由 · 出口也可排序（先按 A→Z）；可以暂停实时刷新；"断开筛选结果"需要二次确认；点一行展开详情（进程路径、目标 IP、规则、完整链路、出口、错误），可以直接"让这个域名走…"生成规则。日志同样支持级别筛选、搜索、暂停、导出。

## 5.2 出口位置从哪来（地图的前提）

节点配置里**没有可靠的地理位置**，只能推断或测量。按可信度排列：

| 来源 | 做法 | 可信度 | 成本 |
|---|---|---|---|
| **实测** | 经该节点访问一个回显服务（如 Cloudflare `/cdn-cgi/trace`，返回出口国家和最近机房代码，例如 `loc=HK colo=HKG`） | 高：测的就是真实出口 | 每个节点一次请求；只测当前在用的节点和用户点开的节点，结果缓存 |
| **按名称** | 解析节点名里的国旗 emoji、国家 / 城市名、地区代码（"香港 03""🇯🇵 Tokyo""SG-01"） | 中：机场节点大多这样命名 | 零成本，作为默认值 |
| 服务器 IP 的 GeoIP | 查节点服务器地址所在地 | **低**：IPLC、中转、CDN 前置时，入口不等于出口 | 不采用，只作参考 |
| 未知 | 以上都没有 | — | 地图上显示虚线和"定位中"，测完再落点 |

实现思路：mihomo 的 `listeners` 可以把一个入站端口绑定到指定代理组；Moho 内置一个探测用的选择器组和专用端口，探测某个节点时把组切到该节点，再经这个端口请求回显服务。界面上用「实测 / 按名称 / 未知」标签标明来源。

## 9. 按什么分流：匹配维度、服务包与虚拟全局（v1.7）

> 起因：想让 ChatGPT 的全部流量（连同遥测）只走一个节点。桌面上现在做得到，但要自己拼三步：在一个路由组里加一条应用规则，把组设为固定节点，再锁定出口（锁定后节点带不了的 UDP 也被拦下，不会漏到别处）。而且 Moho 现在只按两样东西分流：去哪（域名、IP）和谁发的（应用）。这一节把能用来分流的维度列全，定下每个维度在对象模型里住在哪、谁先谁后；把应用代理做成正式功能；再加上一步完成的**虚拟全局**、整窗走一个出口的**专用浏览器窗口**、Moho 自己的**服务包**格式和 `bowel://` 链接。
>
> **状态**（2026-11-22）：9.1 范围、9.5 应用代理、9.7 专用浏览器窗口、9.8 服务包和它的策略、9.9 链接、9.13 隔离还缺什么，用户已经商定。其余（维度放在哪、排序、虚拟全局、预置服务的名单）仍是提案。9.15 是建议并入 §6 的四条。写完之后 main 合并了 #236（锁定组的 UDP、DNS、IPv6 只走节点）和 #234（Android 10 起认得出应用），这一节已按合并后的样子改过。

### 9.1 范围：保证什么，不做什么

**Moho 管网络这一层。** 一个服务、一个应用或一个专用窗口的流量，只从一个固定的出口出去；TCP、UDP、DNS、IPv6 都不会绕过它，从本机网络直接出去；出口走不通就断开，不改道。

**网络之外的不管。** Moho 不改时区、语言、浏览器指纹，不是反检测工具。账号风控还会看这些；Moho 只保证"出口一致、不漏"。

这是目标。锁定组的 UDP、DNS、IPv6 已经补上（#236）；还差退出后断网，以及只按应用认出的流量的 DNS（9.13）。补上之前，界面不说"不会漏"。

### 9.2 五个维度

一条连接到了「规则」这一步，身上带着五样可以判断的东西：三样是链路前几环带来的，两样是连接自己的。

```
设备 ──► 应用 ──► 入口 ──► 规则 ──► 路由 ──► 节点
(哪台设备) (谁发的) (从哪进) (按 去哪 · 什么协议 判断，也看前面三样)
```

| 维度 | 用来做什么 | mihomo 怎么写 | Moho 现在 |
|---|---|---|---|
| **去哪** 目的地 | 按网站、产品分流；绝大多数规则 | `DOMAIN` `DOMAIN-SUFFIX` `DOMAIN-KEYWORD` `GEOSITE` `IP-CIDR` `GEOIP` `RULE-SET` | 有：服务、「我添加的」、规则集（`routes/user.go`、`routes/services.go`） |
| **谁发的** 应用 | 一个程序的全部流量，不管它连哪：遥测、更新、换了域名的接口都跟着走 | `PROCESS-NAME`；macOS 认整个 .app，用 `PROCESS-PATH-WILDCARD`；Android 上 `PROCESS-NAME` 认包名 | 桌面有（`KindApp`），Android 10 起也有（#234）；但只是规则编辑器里的一种规则，内置服务没有 |
| **哪台设备** | 网关上的电视走流媒体节点；某台设备直连或拦截 | `SRC-IP-CIDR`（没有按硬件地址的规则） | 网关认得设备、会发地址（`app_devices.go`、`internal/dhcp`），但不按设备分流 |
| **从哪进** 入口 | 给命令行工具、专用浏览器窗口一扇只通一个路由组的门 | 监听器的 `proxy:`（不经过规则）；`IN-PORT` `IN-NAME` `IN-TYPE` | 有专用端口（`core.ExtraPort`）：一个本机端口绑一个路由组，规则和模式都不看。只能用命令行设（`bowel settings set extraPorts`），界面里没有 |
| **什么协议** | SSH 的 22 端口、BT 的 DHT 端口；拦下 QUIC；给语音和游戏挑能走 UDP 的节点 | `NETWORK` `DST-PORT` `SRC-PORT`，用 `AND` 组合 | 没有。只有出口锁定在内部用 `AND,((NETWORK,UDP),(<规则>)),REJECT` 拦下节点带不了的 UDP |

桌面和 Android 用的 mihomo（v1.19.33）都支持上面这些写法。

### 9.3 每个维度住在哪

**路由组是出口，服务是"认出它"。** 路由组只回答"怎么出去"，服务回答"这是谁的流量"。规则仍然只属于一个服务，服务仍然只属于一个路由组（§1）。

- **路由组**：节点策略（D3）、出口锁定、直接连接（D4a）；新增四个**出口能力**选项：「只用能走 UDP 的节点」「拦下 QUIC」「DNS 走节点」「拒绝 IPv6」，后两个锁定时总是这样（锁的意思就是不漏；#236 已经做了，见 9.13），开关只对没锁定的组有用（要不要见 9.16 第 8 条）；再加上它的**专用端口**。
- **服务**：一个产品的全部认法，分三栏：**网站**（去哪）、**应用**（每个平台一行：Windows 的 exe、macOS 的 .app、Linux 的程序名、Android 的包名）、**端口**（TCP / UDP / 两者，加端口或范围）。导入的服务包也是一个服务（9.8）。
- **设备**：路由组里和服务并列的另一种成员。一台设备只在一个路由组。

| 维度 | 住在 | 为什么 |
|---|---|---|
| 去哪 | 服务 › 网站 | 不变 |
| 谁发的 | 服务 › 应用 | 同一个产品在各端是同一个服务，各端的应用写在一起；生成配置时只写本平台那一行，其他平台的折叠显示。「我添加的」里的应用规则照旧 |
| 什么协议：是哪种流量 | 服务 › 端口 | 用来认出一种协议（SSH、BT），不用来认出一个产品：产品很少有独占的端口。80、443 不能单独写，那是所有网站 |
| 什么协议：出口带不带得了 | 路由组的选项 | "能不能走 UDP""拦不拦 QUIC"说的是这个出口，不是某种流量：同一个 QUIC，直连没问题，走一个 UDP 被限速的节点就慢 |
| 哪台设备 | 路由组 › 设备 | 见下 |
| 从哪进 | 路由组 › 专用端口 | 一扇门只通一个组，本来就是组的属性；设置里只列出来，链接到这里（原则 3） |

**为什么设备不放进服务。** 服务里的各行是"或"的关系：chatgpt.com 或者 ChatGPT.exe，都是 ChatGPT。"ChatGPT = chatgpt.com 或者 客厅电视"没有意义，所以设备单独成一种成员。也考虑过把设备的家放在网关的设备列表里，但 D4 定了结构只在路由组 Tab 编辑。设备列表里给一个「让这台设备走…」的快捷入口，像活动页的「让这个域名走…」（T10），设备落进选中的路由组。

**为什么协议拆成两半。** 也考虑过把协议整个做成服务，比如一个「QUIC」服务放进「拦截」组。这样能拦下所有 QUIC，但直连的 QUIC 也一起拦了，说不出"只拦这个出口的"；"只用能走 UDP 的节点"更不是一种流量。所以认出流量的（端口）进服务，描述出口的（UDP、QUIC、DNS、IPv6）进路由组。

**设备怎么认**

- 按**硬件地址**认，写进配置时换成它现在的地址：`SRC-IP-CIDR,<IP>/32`。地址来自 Moho 发的租约，或者 ARP 表。
- 自动模式（Moho 发地址）：设备进了路由组，它的地址就固定下来，不再过期（现在的租约按硬件地址保留 30 天）。
- 手动模式（路由器发地址）：跟着 ARP 表走，地址变了就重写配置；一个地址换了硬件地址就立刻撤掉，规则不会落到别的设备上。设备行提示"在路由器上给它保留地址更稳"。
- 两种管法：**整台**（它的全部流量走这个组，和应用规则一样），或者**只管它的其他流量**（服务照常认，没被认出的才走这个组，相当于这台设备自己的「其他流量」）。默认整台。
- 允许局域网连接时，手动把代理设成 Moho 端口的设备，来源地址也是它自己的，一样认得出。
- 手机连 Wi-Fi 用"私有地址"时，换一次地址就是一台新设备。设备行提示在手机上对这个网络关掉地址轮换。

**服务详情**（路由组 Tab）：

```
ChatGPT                                      在「AI 服务」   [虚拟全局…]
网站   openai.com · chatgpt.com · oaistatic.com 等 5 个
应用   ChatGPT.exe · codex.exe                      其他平台 3 个 ▸
共用   challenges.cloudflare.com 等 3 个  关         ← 别的网站也在用，出厂不收
```

### 9.4 谁先谁后

现在（D4）的顺序就是列表的顺序：开发者网络（和你落在其中的规则）→ 路由组从上到下 → `MATCH`。组内的先后（应用 → `DOMAIN` → 更长的 `SUFFIX` → … → `GEOIP` → 规则集）只决定连接算在哪条规则上。专用端口不经过规则。

> 注意：D4 已从「越具体越优先」改成严格按列表顺序（#294）。下面的分层提议是按「越具体越先」写的（比如第 3 层"端口排在所有网站规则后面"），要按新的顺序重新考虑。

提议**先按维度分层，层内按 D4**：

| # | 层 | 例子 | 为什么排在这里 |
|---|---|---|---|
| 0 | 专用端口（含专用浏览器窗口） | 7901 → Claude | 不经过规则，进门就定了，模式也不管 |
| 1 | **谁**：整台设备、应用 | 客厅电视；ChatGPT.exe | 说的是"它的全部流量"；排到网站后面，就只剩没被别的服务认出的那一点。两者不会同时命中：网关看不到设备上的程序，本机的程序也不是网关设备 |
| 2 | **去哪** | 按 D4 | 不变 |
| 3 | **端口** | TCP 22；UDP 6881–6889 | 端口不说去哪，比任何网站规则都宽。按 D4 "越具体越先"，它排在所有网站规则后面，只决定没被任何服务认出去哪的连接：github.com 的 SSH 仍跟着 GitHub 走，连自己服务器的 SSH、BT 的 DHT、游戏直接连服务器 IP，才由端口决定 |
| 4 | 设备的其他流量 | 客厅电视（只管其他流量） | 只接住这台设备没被认出的连接 |
| 5 | 其他流量 | `MATCH` | 不变 |

- 规则集只在第 2 层里排（D4）。内置服务和服务包的应用都在第 1 层，也就排在规则集前面；否则装了一个规则集，ChatGPT.exe 的流量可能先被集里的域名认走。反过来，用户自己的端口规则在第 3 层，排在规则集和内置的网站规则后面：D4 的"你的规则 → 规则集 → 内置规则"只管第 2 层。规则集里自带的应用、端口规则，在规则集的位置生效。
- 服务包里的网站规则算你的规则，它带的规则集链接按规则集排。
- 层内仍是用户的规则优先，同样具体时再看路由组的位置（D4）。
- 「拦下 QUIC」在这个组的每条规则**前面**加一行 `AND,((NETWORK,UDP),(DST-PORT,443),(<规则>)),REJECT`（「其他流量」的这一行在 `MATCH` 前面）；出口锁定的 UDP 拦截行在每条规则**后面**。前者是"这个组的 QUIC 不要了"，后者是"节点带不了的 UDP 不许漏到别处"。
- 模式照旧只覆盖「规则」这一步：全局 / 直连模式下，设备、应用、端口规则和其他规则一样让位；锁定的组例外，规则留在原位。专用端口不受模式影响。

### 9.5 应用代理（已商定）

现在要代理一个应用，得知道规则编辑器里有「应用」这一种，再自己去组里设节点。把它做成正式功能，三步：

1. **选应用**：用现有的应用选择器（`ui_apppicker.go`：正在运行的、有连接的，一点就选）。
2. **选出口**：放进一个现有的路由组，或者给它新建一个组、固定一个节点。
3. **可选：锁定出口**（非连即断）。

做完是一个只有应用的服务（名字和图标取应用的），在选中的路由组里；选"新建一个组"，就是对这个服务做虚拟全局（9.6）。它和服务包里"只有应用、没有网站"的写法是同一个东西（9.8）。

- **入口**：路由组 Tab 的「代理一个应用…」；活动页连接详情的「让这个应用走…」。
- **只开了系统代理时要说**：应用可以不认系统代理，直接连出去，这时应用规则管不到它，锁定也拦不住。选完应用就提示"只开了系统代理：这个应用不一定经过 Moho。[打开 TUN]"；锁定时这句是警告，不是提示。
- 选到浏览器、node 这类程序时的提示见 9.10 的原则 1、2。
- Android 10 起认得出应用（#234，按包名），包名从一开始就写在服务里；更早的 Android 和 iOS 认不出。

### 9.6 虚拟全局

**虚拟全局是一个服务自己的全局模式**：这个服务的全部流量只走一个节点，走不了就断开；其余流量照常分流。

它不是新对象，而是一步操作，做完得到一个普通的路由组：

1. 服务单独成组（现有的「单独成组」，`SplitService`，组名取服务名）。已经独占一个组的服务不再拆。
2. 节点策略设为**固定节点**，默认是它现在的出口。
3. 打开**出口锁定**：只走这个节点。节点不通、关闭接管、切到全局或直连模式时，都不改走别处；节点带不了的 UDP 被拦下，QUIC 退回 TCP；它的域名经节点问 DNS，IPv6 也只走节点（#236）。

```
虚拟全局 · ChatGPT
这个服务的全部流量只走一个节点，走不了就断开。

节点    🇺🇸 洛杉矶 VPS · 168 ms · 出口 203.0.113.7（实测）        [换]
        这个节点不支持 UDP：需要 UDP 的功能（语音通话）可能用不了
认出它  网站 5 个 · 应用 ChatGPT.exe、codex.exe
入口    TUN 已开 · 网页里的第三方请求要一起走，用专用窗口   [打开窗口]
锁定    DNS 经节点问，IPv6 只走节点，节点带不了的 UDP 拦下
☐ 拦下 QUIC   ☑ 出口 IP 变了提醒我

                                         [取消]   [开始虚拟全局]
```

- 这个面板也是服务包策略的确认面板（9.8）：导入时按策略填好，每一项都能改。
- **入口**：路由组 Tab 的服务行；活动页一条连接的详情（「让 ChatGPT 虚拟全局…」）；应用代理选"新建一个组"时。
- **撤销**：路由组详情里的「合并回 AI 服务」：服务搬回原来的组，空组删掉。
- **账号风控**：固定节点的出口 IP 也会变（机场换了机器，节点名没变）。虚拟全局的组默认在实测出口 IP 变化时提醒一句（§5.2 的实测；降级态，一句话）。只在乎地区、不在乎 IP 的，用自动最快限定地区 + 锁定（D3：范围里没有节点时变红，不悄悄放宽）。时区、语言、指纹不归 Moho 管（9.1）。
- **命令行工具**：跑在 node、python 里的工具认不出是谁，加成应用规则会把所有 node 程序都收进来。用这个组的专用端口启动它：`HTTPS_PROXY=http://127.0.0.1:7901`；开发工具（`internal/devtools`）以后可以直接把某个工具指向这个端口。
- **网页**：TUN 下浏览器的流量只能按域名认，页面引用的第三方（Cloudflare 人机验证、统计、客服插件）按各自的规则走。要整页都走这个出口，用专用浏览器窗口（9.7）。
- iOS 认不出应用，只按网站。

### 9.7 专用浏览器窗口（已商定）

**为什么分不出标签页。** 代理客户端看到的是浏览器的网络进程：所有标签页的流量都从这一个进程出去，连接还在标签页之间共用。浏览器自己能不能分：

- **Firefox** 可以：扩展的 `proxy.onRequest` 拿得到 `tabId`，能按标签页或容器分流。没有标签页的请求（service worker 等）`tabId` 是 -1，要一个默认去处。
- **Chrome、Edge** 不行：`chrome.proxy` 管的是整个配置文件，PAC 只看得到网址。

**所以主功能是专用窗口，各家浏览器都能用。** Moho 另起一个浏览器实例，用它自己的配置文件，代理指向这个路由组的专用端口（`ExtraPort`；组还没有就分配一个）：

```
chrome --user-data-dir=<Moho 数据目录>/browser/<组>
       --proxy-server=http://127.0.0.1:<端口>
       --force-webrtc-ip-handling-policy=disable_non_proxied_udp
       <网址>
```

- 这个窗口里的每个标签页，连同页面加载的第三方资源，都从这个组出去；别的窗口不受影响。专用端口不经过规则（9.4 第 0 层），所以国内网站在这个窗口里也走这个组：整个窗口一个出口。
- WebRTC 只能经代理（上面最后一个参数），不会从本机网络探出地址。
- 配置文件按路由组固定，登录状态留着；和用户平时的浏览器配置文件分开，不读也不改它。
- Chrome、Edge、Brave 等 Chromium 系都用这几个参数。Firefox 没有 `--proxy-server`：用 `-profile <目录> -no-remote` 起它，代理和 WebRTC 的设置写进那个配置文件的 `user.js`。
- **入口**：路由组详情「在专用窗口中打开」；虚拟全局面板；服务包的策略要求窗口时，确认后直接给出这个按钮。
- 以后可选：一个 Firefox 扩展，按标签页或容器分流。

### 9.8 服务包（已商定）

**不加载整份 mihomo 配置。** GitHub、gist 上常见整份配置，但加载它会让 Moho 进入 D1 的"使用配置自带的路由"：你的规则暂停，出口锁定也用不了；远端配置还能把流量指到别人的节点上。所以 Moho 有自己的格式：**服务包**。

导入的服务包就是一个服务，规则从来源来，和规则集一样。预置服务（9.10）也是同一种东西，只是随 Moho 发布。

**里面有什么**

| 字段 | 内容 |
|---|---|
| 名字 | 服务名 |
| 网站 | 写法同内置服务：一个域名是它和它下面的所有名字；`full:` 仅此域名；`keyword:` 关键词；IP 段；`geo:` / `geoip:` 内置库 |
| 规则集 | 0 个或多个链接，和导入的规则集一样下载、更新 |
| 应用，按平台 | Windows：exe 名。macOS：.app 名，还可以写 bundle id（改了名、本地化名字不同时，Moho 按 id 找到装着的那个 .app）。Android：包名。Linux：程序名 |
| 策略（可选） | 推荐的出口设置，见下 |
| 网址（可选） | 策略要求专用窗口时，窗口打开它 |

- 应用一项的意思是**这个应用的全部流量**，排在网站规则前面（9.4 第 1 层，和现在的 `KindApp` 一样）。所以只写应用、不写网站的服务包，就是"代理这一个应用"。
- **不含节点，也不含 DNS 服务器。** 节点只从 Provider 来（D1）。
- 端口不进服务包（第一版）：别人写的一条宽端口规则会把无关的流量收进来。

```yaml
name: ChatGPT
domains: [chatgpt.com, openai.com, oaistatic.com, oaiusercontent.com, sora.com]
apps:
  windows: [ChatGPT.exe]
  macos: [{name: ChatGPT.app, id: com.openai.chat}]
  android: [com.openai.chatgpt]
policy:
  group: new
  lock: true
  strategy: {fixed: US}
  udp: true
  dns: node
  ipv6: refuse
  quic: allow
  entry: tun
```

**策略**

| 字段 | 取值 | 落到 |
|---|---|---|
| `group` | `new`：新建一个组，名字取服务名；或者内置组的 id（`ai` `media` `dev` `direct` `reject` `default`） | 服务放进哪个组。别的写法，或者那个组已被删掉，就在确认面板里让用户选 |
| `lock` | 是 / 否 | 出口锁定（非连即断） |
| `strategy` | `{fixed: US}` 固定节点，导入时在这个地区的节点里挑一个；`{region: [US]}` 自动最快，限定地区；`{order: [US, JP]}` 顺序备用，每个地区挑一个节点，按这个顺序 | 节点策略（D3）。服务包不知道用户有哪些节点，所以只写地区，节点在确认面板里挑 |
| `udp` | 是 / 否 | 「只用能走 UDP 的节点」 |
| `dns` | `node` | 「DNS 走节点」（9.13 a）。`lock: true` 时总是这样，这一项只对没锁定的组有用 |
| `ipv6` | `refuse` | 「拒绝 IPv6」（9.13 b）。同上 |
| `quic` | `allow` / `block` | 「拦下 QUIC」 |
| `entry` | `tun` / `window` | 要求的入口：`tun` 时 TUN 没开就提示打开；`window` 时确认后给出「在专用窗口中打开」 |

- 策略**只在第一次导入、用户确认后**套用。确认面板就是虚拟全局的面板（9.6），按策略填好，每一项都能改。
- 更新**只改规则**，像规则集一样；不动策略，也不动用户后来的改动（组、节点、锁）。
- 提议：更新**新加了应用**时，要用户点一次同意。一个应用就是它的全部流量，悄悄加进一个浏览器，就等于把整个浏览器换了出口。同意之前新应用不生效，服务行上一句话说明。
- 网站和现有服务重了：一条规则只属于一个服务，导入后归这个服务包（现有的 `Claim`）。确认面板写明"chatgpt.com 等 5 个现在在「OpenAI」里，导入后归这里"。

**来源**

- 只收 HTTPS 链接或本地文件。
- GitHub 的文件页链接（`github.com/<用户>/<仓库>/blob/<分支>/<路径>`）换成 `raw.githubusercontent.com/<用户>/<仓库>/<分支>/<路径>`；gist 的页面链接（`gist.github.com/<用户>/<id>`）换成它的 raw 链接（多个文件时要指明哪一个）。
- 和规则集一样定时更新。
- 入口：路由组 Tab 的「导入」，和导入规则集放在一起；任何页面粘贴链接时按内容认出是服务包、规则集还是订阅；`bowel://add-pack`（9.9）。

### 9.9 链接（已商定）

- `bowel://add-pack?url=<服务包链接>`、`bowel://add-provider?url=<订阅链接>`。
- 可选接收 `clash://install-config?url=…`：粘贴和扫码时 `provider.Unwrap` 已经认得这类安装链接。注册 `clash://` 会和装着的其他 Clash 客户端抢，所以在设置里由用户打开，默认不注册。
- **从不悄悄生效。** 任何网页都能触发这种链接。Moho 打开窗口，显示来源的域名、包里有什么（网站几个、应用哪些）、它要的策略，等用户确认；订阅也一样，显示来源域名再添加。

| 平台 | 怎么注册 | 链接怎么到 bowel |
|---|---|---|
| Windows | `HKCU\Software\Classes\bowel` | 命令行参数 |
| macOS | Info.plist 的 `CFBundleURLTypes` | Apple 事件（`application:openURLs:`），不是命令行参数：要 MyGo 转给 bowel |
| Linux | `.desktop` 里写 `MimeType=x-scheme-handler/bowel;`，`Exec=bowel %u` | 命令行参数 |
| Android | `intent-filter`（`<data android:scheme="bowel"/>`） | Intent |

第一次启动和已经在运行，两种都要处理。`cli.WantsGUI` 已经把带 `://` 的参数当成打开界面；已在运行时，MyGo 的 `OnSecondInstance` 已经把参数传给 `App.onSecondInstance`（`app.go`），只是现在没用它们。

### 9.10 预置服务

预置服务是随 Moho 发布的服务包，没有策略，落在默认的路由组里。现有的内置服务（`routes/services.go`）只有网站；这里给它们补上应用，再加几种常见需要。原则：

1. **只收这个产品独占的程序。** 浏览器、Google 应用（Android 上的 Gemini 常常就在它里面）、微信这类装着很多产品的程序，不进任何服务。用户自己把浏览器加成应用时提示："浏览器里的所有网站都会走这里，包括国内网站"，并建议改用专用窗口。
2. **通用的宿主进程不当应用**：node、python、java，以及 Windows 的 svchost.exe（Windows 更新、DNS 都在里面）。选到它们时，建议改用专用端口。
3. **共用的第三方域名出厂关闭。** 人机验证、统计、客服、支付（`challenges.cloudflare.com`、Intercom、Sentry、Stripe 这类）会把别的网站一起带过来。它们作为服务里的「共用」规则出厂关闭（内置规则本来就能单独关），用户在虚拟全局里明确打开；要整页都走，用专用窗口更彻底。一条规则只属于一个服务：打开时如果别的服务已经有它，就移过来（`Claim`），并说明那边少了什么。
4. **一个产品可以是几个服务。** Steam 的商店要走节点，下载走国内能直连的 CDN，所以是两个服务。虚拟全局作用在服务上，不在产品上。
5. **一份定义，各端共用。** 应用按平台各写一行，生成配置时只写本平台的；产品逻辑是平台无关的 Go 包（§8），手机的配置从桌面的 Go 生成。
6. **上线前在各平台抓一次连接核对**（活动页按应用筛选），下表标「待核对」的尤其要核对。

### 9.11 场景

| 场景 | 怎么做 | 用到 |
|---|---|---|
| 一个服务全部走代理（ChatGPT 连同遥测） | 虚拟全局；网页要连同第三方一起走，再开专用窗口 | 服务的应用和网站；固定节点；锁定；专用窗口 |
| 代理一个应用 | 应用代理：选应用、选出口、可选锁定 | 应用；9.5 |
| 网上分享的分流（GitHub、gist） | 导入服务包，按它的策略确认一次 | 9.8；`bowel://add-pack` |
| 固定出口地区或 IP（账号风控） | 要同一个 IP：虚拟全局，出口 IP 变了提醒。只要同一个地区：自动最快限定地区 + 锁定。时区、语言、指纹不管（9.1） | D3 的范围；§5.2 实测 |
| 大流量下载直连或走指定节点（Google Play、Steam、系统更新） | 「Steam 下载」「系统更新」出厂直连。要走节点的（Google Play）移到一个"下载"组，节点策略限定一个不限流量的 Provider | 服务；D3 的来源 |
| P2P / BT 直连或拦截 | 「BT 下载」出厂直连；移到「拦截」就不让下。网关上的 NAS 认不出程序：把它整台放进去，或者靠 DHT 端口 | 应用；端口；设备 |
| 游戏和语音，要能走 UDP 的节点 | 新建路由组，打开「只用能走 UDP 的节点」，把游戏程序、Discord 放进去。锁定后，节点带不了的 UDP 被拦下，不会悄悄改走别处 | 组选项；应用 |
| 拦下 QUIC（UDP 443） | 在那个路由组上打开「拦下 QUIC」：网页退回 TCP，走节点更稳；直连的 QUIC 不受影响 | 组选项 |
| SSH、git 的 22 端口 | github.com 的 SSH 跟着 GitHub（开发）走；没开 TUN 时由开发工具里的 git SSH 接到代理。节点封了 22 端口时，活动页提示改用 `ssh.github.com:443`，或者把 GitHub 移到一个不封的节点。连自己的服务器：打开「SSH」（直连），或者把它移到连得上的组 | 端口；开发工具 |
| 网关上的局域网设备（电视走流媒体节点） | 设备列表里「让这台设备走…」：选流媒体，或者它自己的组（固定一个解锁目标地区的节点）。电视也看国内视频时，选"只管它的其他流量" | 设备 |

### 9.12 冲突，和界面怎么说

按 9.4 的顺序，每条连接只有一个结果。要做的是在用户会困惑的地方把"为什么"说出来，说在三处：服务详情（这里管什么，谁拿走了一部分）、活动页的连接详情（命中了什么，没有它会走哪）、路由组 Tab 的「测试一个地址」（可以选"从哪个应用 / 设备发出"，答案按应用分开写）。

| 冲突 | 结果 | 怎么说 |
|---|---|---|
| 应用在 A，它访问的网站的服务在 B（Chrome 整个放在「A」，Claude 在「AI 服务」） | 应用赢：在 Chrome 里打开 claude.ai 走 A | Claude 的服务详情："从 Chrome 发出的不走这里：Chrome 整个在「A」"。连接详情："命中 应用 Chrome（A）；没有这条会走 Claude（AI 服务）" |
| 同一个应用加进第二个服务 | 不会两处都有：从原来的服务移走（`Claim`） | "ChatGPT.exe 已从「OpenAI」移到这里" |
| 服务包的网站和现有服务重了 | 归服务包（`Claim`） | 确认面板里列出来（9.8） |
| 服务包更新新加了应用 | 同意之前不生效 | 服务行一句话 + 同意 |
| 端口在 A，网站在 B（SSH 在直连，GitHub 在开发） | 网站赢：github.com 的 SSH 走开发 | SSH 的服务详情："只管没被其他服务认出的连接；github.com 的 SSH 跟着 GitHub" |
| 整台设备 vs 服务 | 整台：设备赢。只管其他流量：服务赢 | 设备行写明是哪种管法 |
| 专用端口、专用窗口 vs 一切 | 专用端口赢，规则和模式都不看，国内网站也走这个组 | 连接详情："从专用端口 7901 进来"；窗口的连接写"专用窗口 · ChatGPT" |
| 节点不支持 UDP，组没锁 | mihomo 跳过这条规则，UDP 落到后面的规则，常常是其他流量 | UDP 连接的详情："「AI 服务」的节点不支持 UDP，落到了其他流量"，并给两个办法：只用能走 UDP 的节点、锁定出口 |
| 节点不支持 UDP，组锁了 | 拦下，QUIC 退回 TCP | "出口锁定 · 节点不支持 UDP，已拦下" |
| 只开了系统代理 | 不认系统代理的应用直接出去，应用规则和锁定都管不到 | 应用代理和锁定时提示打开 TUN（9.5） |
| 用着 Provider 自带的路由（D1） | 服务、服务包、设备、虚拟全局、组选项都暂停 | 和出口锁定一样："导入的配置里没有 Moho 的路由组" |

**DNS 不算在应用名下。** 应用解析域名时，查询多半不是它自己发出的：Windows 上是 DNS Client 服务（svchost.exe），macOS 上是 mDNSResponder，Linux 上常是 systemd-resolved。所以应用规则管的是应用的连接，管不到它的 DNS 查询。好在走节点的连接用不着在本机解析：

- TUN（fake-ip）下，A / AAAA 查询由 Moho 在本机回一个假地址，连接带着域名到节点那头再解析；只有直连的、在 fake-ip 过滤名单里的域名，以及 A / AAAA 以外的查询，才问上游（9.13 a 补上的就是最后这一种）。
- 系统代理和专用窗口下，浏览器把域名交给代理，同样不在本机解析。
- 应用自己做的 DNS over HTTPS 是它的普通连接，跟着应用规则走。

所以 DNS 要靠路由组按域名把查询送去节点，不靠应用规则。只写了应用、没写网站的服务，它的这类查询说不出属于谁，还是直接问（9.13 a）。网关设备的查询也都问 Moho（53 端口），情况相同。

### 9.13 隔离还缺什么（已商定）

出口锁定原来只管住了 TCP。要做到 9.1 说的"不漏、走不通就断"，差下面几处。a、b、d 已经由 #236 补上（2026-11-22 合并），还剩 c 和 a 的一个缺口：

| # | 漏在哪 | 现在 | 怎么补 |
|---|---|---|---|
| a | DNS | 原来：默认 fake-ip；上游是国内的 DoH（doh.pub、dns.alidns.com），用 223.5.5.5、119.29.29.29 查它们自己的地址，都从本机网络直接问；「DNS 遵循规则」（`respect-rules`）默认关。A / AAAA 以外的查询（比如 HTTPS 记录）不回假地址，而是从真实 IP 问上游：锁定组的域名就这样被看到。**已补**（#236）：锁定组的域名（后缀、整个域名、GeoSite、域名或整条规则的规则集）加了 `nameserver-policy`，服务器后面带 `#<组名>`，查询经这个组的节点发出，没有节点可走就不问；走不了代理的服务器（system、DHCP、tailnet 的）不放进去 | 还剩：关键词规则和应用规则说不出域名。只写了应用的服务（应用代理做出来的就是这种），它的 A / AAAA 以外的查询照旧直接问。提案：从活动页记下这个应用连过的域名，提议加进服务的网站；关键词提议改写成后缀 |
| b | IPv6 | 原来：内核的 IPv6 关着时，TUN 没有 IPv6 地址，不接 `2000::/3` 和 `::/0` 的其余部分：应用直接用 IPv6 连出去，绕过锁定。**已补**（#236）：有组锁定、开着 TUN 时，TUN 也接 IPv6，和 IPv4 一样过规则：锁定组的只走节点，其余照旧从本机出去；DNS 仍不回 IPv6 地址，应用照旧用 IPv4。用的是"接进 TUN"，没用 strict-route。Android 不用补：VPN 没给路由的地址族，系统直接拦下 | — |
| c | Moho 退出、内核崩溃之后 | 规则随内核一起没了，流量回到本机网络（锁定的说明里已经写着"退出 bowel 后不再拦截"） | 用系统防火墙：Windows WFP、macOS pf、Linux nftables，要管理员权限。Android 用系统的「始终开启的 VPN」和「屏蔽未使用 VPN 的连接」，Moho 引导用户去打开 |
| d | UDP | **已补**（#236）：锁定组的每条规则后面跟一行同样匹配的 UDP，送去 REJECT。节点带得了 UDP 的照走，带不了的拦下，QUIC 退回 TCP | — |

### 9.15 建议并入 §6 的四条

| # | 决策 | 状态 | 结论 |
|---|---|---|---|
| D7 | 匹配维度放在哪、谁先谁后 | 提案 | 路由组是出口：节点策略、出口锁定、直接连接，加上「只用能走 UDP 的节点」「拦下 QUIC」「DNS 走节点」「拒绝 IPv6」（后两个锁定时总是这样）和它的专用端口。服务是认出一个产品的全部方式：网站、各平台的应用、端口。设备是路由组里和服务并列的成员，按硬件地址认，分「整台」和「只管其他流量」。顺序：专用端口（不经过规则）→ 整台设备、应用 → 去哪（D4）→ 端口 → 设备的其他流量 → 其他流量。D4 的排序只管「去哪」这一层；内置服务和服务包的应用也排在规则集之前。 |
| D8 | 应用代理、虚拟全局、专用窗口 | 应用代理、专用窗口已商定；虚拟全局是提案 | 应用代理是正式功能：选应用、选出口（现有组，或新建一个固定节点的组）、可选锁定；只开系统代理时提示。虚拟全局一步让一个服务的全部流量只走一个节点：单独成组、固定节点、锁定，出口 IP 变了提醒。专用浏览器窗口：独立的配置文件，代理指向组的专用端口，WebRTC 只经代理；Firefox 扩展以后再说。 |
| D9 | 服务包与链接 | 已商定 | 不加载整份 mihomo 配置。服务包含名字、网站规则、规则集链接、各平台的应用（Windows exe、macOS .app 和 bundle id、Android 包名、Linux 程序名），不含节点和 DNS 服务器；应用一项是它的全部流量。策略（组、锁定、节点策略、UDP、DNS、IPv6、QUIC、入口）只在第一次导入、用户确认后套用，更新只改规则。来源是 HTTPS 链接或本地文件，GitHub 和 gist 的页面链接换成 raw。`bowel://add-pack`、`bowel://add-provider`，`clash://install-config` 由用户打开；从不悄悄生效。 |
| D10 | 范围 | 已商定 | Moho 保证网络层：一个固定出口；TCP、UDP、DNS、IPv6 都不直接漏出去；走不通就断。不改时区、语言、浏览器指纹，不是反检测工具。 |

并入时同步改 §1：「规则」一行加上设备、端口；「服务」一行改为"一个网站或产品的全部认法：网站、应用、端口"，并说明服务包导入后就是一个服务；命名统一那句加上「设备」「服务包」。「虚拟全局」是一个操作的名字，不是新对象。§4 的 Provider 页：粘贴时按内容认出服务包，转到路由组 Tab 导入。

### 9.16 待确认

1. **共用的第三方域名**：有了专用窗口，还要不要出厂带着（关闭）？还是单独做一个「共用」服务，或者不提供？打开后会把别的网站一起带过来，而 Moho 不知道是哪些，只能从活动页的历史里列出见过的。
2. **专用窗口用哪个浏览器**：默认浏览器是 Chromium 系或 Firefox 就用它；是 Safari 时（不支持这些参数）用装着的哪一个？要不要给窗口一个看得出来的标记（主题色、窗口标题），免得和平时的浏览器混？
3. **服务包的更新**：新加应用要用户同意（9.8 的提议）是否同意？去掉应用、改网站要不要也说一句？
4. **服务包的边界**：要不要带端口（第一版不带）？只显示来源域名够不够，要不要签名或校验？`group` 只认内置组的 id 够不够？
5. **端口排在网站之后**：这样 github.com 的 SSH 不能单独改道。要不要支持"端口 + 网站"的组合规则（`AND`），还是靠 `ssh.github.com:443` 就够了？除了 80、443，还要禁止哪些端口单独写（53？）？
6. **设备的默认管法**：整台，还是只管其他流量？电视既看 Netflix 又看国内视频时，两种都不完美；真正的"这台设备一套自己的规则"要用 mihomo 的 `SUB-RULE`，是否先不做？
7. **能不能走 UDP 怎么判断**：先按节点配置判断（http 不能；ss、vmess、trojan、vless、socks5 看 `udp`；hysteria、tuic、wireguard 本来就走 UDP），还是要实测（经节点发一次 UDP 查询）？配置写了 `udp: true` 但服务端不支持的，只有实测才知道。
8. **「DNS 走节点」「拒绝 IPv6」要不要开关**：#236 让锁定的组总是这样（IPv6 是接进 TUN 再按规则走，没用 strict-route）。没锁定的组要不要这两个开关？不要的话，服务包的 `dns`、`ipv6` 两个字段就省掉，跟着 `lock` 走。
9. **退出后断网**：要管理员权限，什么时候请求，默认开不开？
10. **出厂状态**：SSH 出厂关闭，失败时提示。BT 出厂直连，对不想让运营商看到 BT 的人是不是太激进，要不要也出厂关闭？Steam 下载、系统更新出厂直连，会让升级后的一部分流量改道，要不要在升级时说一句？
11. **WebRTC**：专用窗口里已经只经代理。不在窗口里时，风控脚本用 STUN（UDP）探出的地址走的是其他流量的出口，和页面的出口不一致，要不要处理？
12. **iOS**：只认得出网站。虚拟全局在 iOS 上照样提供并写明这一点，还是不提供？
13. **Windows 的传递优化**（Delivery Optimization：和别的电脑 P2P 传更新，TCP 7680）算不算进「系统更新」？
14. **游戏**：只给"游戏与语音"一个新建路由组的模板（只用能走 UDP 的节点 + 自动最快），还是也带几个游戏服务？

### 9.17 实现顺序

1. **应用代理做成正式功能**：选应用、选出口、可选锁定，只开系统代理时提示；内置服务补上各端的应用（带平台）和出厂关闭的规则；虚拟全局面板（单独成组、固定节点、锁定都已经有了，主要是界面）；连接详情里的"没有这条会走哪"。这一步就解决了最初的问题。
2. **补隔离**（9.13）：d、b 和 a 的大部分已经由 #236 做完；还剩只写了应用的服务的 DNS（a），和第 10 步的退出后断网（c）。都补完之前，界面不说"不会漏"。
3. **路由组的出口能力**：「只用能走 UDP 的节点」（节点能力从 Provider 的配置里读，并进 D3 的范围）、「拦下 QUIC」；「DNS 走节点」「拒绝 IPv6」的单独开关看 9.16 第 8 条。
4. **专用浏览器窗口**：专用端口进路由组详情；Chromium 系用参数启动，Firefox 写 `user.js`。
5. **服务包**：格式、导入（HTTPS 或本地文件，GitHub 和 gist 的页面链接换成 raw，粘贴时按内容认出）、策略确认面板（复用虚拟全局面板）、更新。
6. **链接**：`bowel://add-pack`、`bowel://add-provider`，四个平台注册，第一次启动和已在运行都处理（macOS 要 MyGo 转来 Apple 事件）；可选的 `clash://install-config`。
7. **端口规则**：新的规则种类，`rank` 加一层；预置 BT 下载、SSH。
8. **出口 IP 变化提醒**：用 §5.2 的实测。
9. **设备**：硬件地址换成地址、固定租约、地址变了重写配置；设备列表里的快捷入口；活动页的搜索加上 `device:`。
10. **退出后断网**（9.13 c）：系统防火墙，要管理员权限；Android 引导到系统设置。
11. 以后可选：Firefox 扩展，按标签页或容器分流。

Android 10 起的应用规则已经有了（#234）；内置服务从第 1 步起就带着包名。
